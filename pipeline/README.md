# Конвейер

Реестр документов, постраничный индекс и чтение страниц. Задачи #1 и #6.

```bash
python -m pipeline.cli objects
```

```bash
python -m pipeline.cli registry --object OBJ-TYUMENSKAYA-5-GOLD-SEED
```

```bash
python -m pipeline.cli pages --object OBJ-TYUMENSKAYA-5-GOLD-SEED --workers 8
```

Результат: `build/<объект>/documents.jsonl` и `pages.jsonl` по схемам из `contracts/`.

## Идентификаторы файлов

Берутся из реестра организатора по SHA-256 содержимого, а не по имени и не по пути.
Имена корпуса приехали в кодировке cp866, часть восстановлена, часть нет, а манифест
организатора ссылается на исходные пути. Сопоставление по содержимому переживает
и переименование, и перепаковку.

Проверено: на объекте Тюменская-5 все 57 файлов получили официальные идентификаторы.
Файлы, которых в реестре нет (наши дополнительные объекты), получают локальный
идентификатор с префиксом `L`. Перепутать нельзя: официальные начинаются с `F`.

## Что с чем читается

| Тип страницы | Текстовый слой | Tesseract | Модель |
|---|---|---|---|
| Обычный текст | да | нет | нет |
| Плотный текст | да | нет | нет |
| Чертёж | да | нет | **да** |
| Скан с редкими словами | да | **да** | нет |
| Скан без текста | нет | **да** | **да** |

Распределение не угадано, а взято из замеров стенда.

Tesseract не запускается на чертежах: там он не дал ни одного значения сверх
текстового слоя (13 из 14 у обоих), зато на листе А1 при 300 dpi съедает до тридцати
секунд. Модель не запускается на разреженных сканах: там обе колонки дали 5 из 5.
Оговорка: на разреженных сканах эталон тонкий, всего пять значений, и решение стоит
перепроверить, когда эталон вырастет.

Эти два сужения дали на тестовом файле ускорение в двенадцать раз и снижение
стоимости в тридцать четыре раза: 36 страниц за 25 секунд и 0,004 доллара вместо
5 минут 15 секунд и 0,14 доллара.

## Кеш

Чтение кешируется по SHA-256 файла и номеру страницы в `.cache/pages/`.
Повторный прогон бесплатен. Чтобы перечитать заново, удалите каталог.

Текст страниц для правил и остальных разборов собирается в два слоя.

- **Сырой слой PDF** — `.cache/layer/` по SHA-256 документа (`matrix_rules.raw_layer`). Зависит
  только от байтов файла и версии PyMuPDF и не стареет с кодом. Открыть PDF и вынуть слой —
  самое дорогое в чтении: 5–10 мс на страницу.
- **Текст страниц** — `.cache/text/v<формат>/` (`matrix_rules.page_texts_src`): слой после починки
  кодировки (#98) и подстановки распознанного из кеша чтения — если слоя нет (#52), шаг чтения
  назвал страницу сканом со штампом (`SCAN_SPARSE`) или слой короче 30 знаков (#116). Строка помнит
  отпечаток кода обработки (`pf`); правка обработки пересобирает текст из сырого слоя, не открывая
  PDF. Строка из распознанного помнит слой и время записи файла кеша чтения: страница, перечитанная
  позже, обновляется сама. Сравнение редакций читает у скана со штампом слой (`scans=False`).

Кандидаты правил Матрицы кешируются по «документ × правило» в `.cache/rule_candidates/`
(`matrix_rules.document_candidates`). Ключ документа — путь, стадия и отпечаток прочитанного
текста; у каждого правила — отпечаток (`rule_fingerprint`): поля правила, которые читает разбор
(не примечание, не основание и не сравнение), перечень классов и отпечаток кода разбора его вида
(`pipeline/fingerprint.py` — хеш синтаксического дерева без комментариев). Разбирается заново
только правило с новым отпечатком; три последних варианта правила хранятся, так что откат правки
бесплатен. Номер версии руками поднимать не нужно: `CANDIDATES_VERSION` — ручная эпоха на случай,
когда разбор стал зависеть от данных вне кода.

Замер 24.09, девять объектов, все очереди (Р-87): тёплый прогон — около 40 с; правка одного
правила — плюс секунды; правка примечания или сравнения — ноль разбора; правка модуля одного вида
(`fire_doors.py`) — разбор только его правил; правка обработки текста — пересборка текста из слоя
без чтения PDF.

**Пересобрать заново по требованию** — для случаев, которых отпечаток не видит (внешние данные,
новая PyMuPDF), или чтобы проверить, что кеш не врёт:

| что | команда | переменная окружения |
|---|---|---|
| текст и кандидаты всех правил | `cli rules --fresh`, `cli run --fresh` | `PIPELINE_FRESH=all` |
| слой PDF и текст страниц | `--fresh-text` у `rules`, `run`, `free`, `acts`, `rooms`, `plans`, `revdiff` | `PIPELINE_FRESH=text` |
| кандидаты всех правил, текст из кеша | `cli rules --fresh-candidates` | `PIPELINE_FRESH=candidates` |
| кандидаты отдельных правил | `cli rules --fresh-rules AR-045,KR-055` | `PIPELINE_FRESH_RULES=AR-045,KR-055` |
| ответы модели по чертежам (платно) | `cli vlm --fresh`, `cli run --vlm --vlm-fresh` | — |

Переменные окружения читают все шаги, инструменты замера и воркер сервиса (в `docker-compose.yml`
они прокинуты воркеру). Документ пересобирается один раз за прогон; воркер сбрасывает этот учёт
перед каждым сравнением.

## Параллельность

Страницы читаются одним пулом процессов на объект (`pages.build`): распознавание упирается
в процессор, запрос к модели в сеть, и вместе они хорошо перекрываются. Пул общий для всех
документов — у исполнительной документации сотни файлов по странице, и пул на документ
держал занятыми один-два потока из шести (#113). В процессе открыт один документ:
документы, открытые рядом в одном процессе, делят склад ресурсов MuPDF, и отрисовка страницы
начинает зависеть от соседа.

Угол листа (`titleblock_ocr`) читается тоже процессами, по порядку страниц. Файл открывается
раз на процесс, а не раз на страницу — том ИД одним PDF на тысячи страниц открывается
секунды, — и перед каждой отрисовкой склад MuPDF очищается, чтобы угол выходил как из только
что открытого файла (Р-90).

## Поток данных

Один объект проходит семь шагов; каждый читает предыдущий и ничего не перечитывает:

```
папка объекта
  │  registry   реестр документов: SHA-256, стадия, раздел, идентификаторы организатора
  ├─ documents.jsonl
  │  pages      постраничный индекс: текстовый слой, распознавание, тип страницы
  ├─ pages.jsonl                 (кеш .cache/pages по SHA-256, повторный прогон бесплатен)
  │  sheets     основная надпись: шифр, номер листа, стадия, редакция
  ├─ sheets.jsonl
  │  revisions  стадия, марка, редакция, цепочки редакций — проверенные содержимым, выпуски по папкам (#10, #19, #110)
  │  revdiff    что изменилось между редакциями: страницы, строки, места на листе, отметки (#19, #81)
  ├─ revisions.jsonl, revision_diff.jsonl, findings_revisions.jsonl
  │  rooms      экспликации: номер, наименование, площадь, категория
  ├─ rooms.jsonl, rooms_report.json
  │  plans      помещения и марки систем на чертежах
  ├─ plan_rooms.jsonl, hvac_systems.jsonl, sheet_pairs.jsonl
  │  acts       акты освидетельствования из XML и их сверка с рабочей документацией
  ├─ acts.jsonl, findings_acts.jsonl
  │  rules      правила Матрицы: значение в двух стадиях и сравнение
  ├─ findings_matrix_q1…q5.jsonl, applicability_q4.jsonl, readiness.json
  │  free       свободный поиск: предусмотрено проектом для помещений — нет в рабочей документации;
  │             экспликации между стадиями (#56)
  ├─ findings_free.jsonl
  │  submit     проекция находок в формат сдачи организатора
  └─ submission.json
```

Сервис (`service/worker/steps.py`) выполняет те же команды: шаг `parse` — реестр, страницы,
связку листов и акты; шаг `compare` — правила; шаг `protocol` — проекцию и протокол.

## Версии в протоколе

| Поле | Формат | Что означает |
|---|---|---|
| `matrix_version` | `q1-<хеш>+q2-<хеш>+…+q5-<хеш>` | по хешу каждого файла правил: меняется от любой правки порога или регулярного выражения |
| `dataset_version` | `manifest-<хеш>` в протоколе, `ds-<хеш>` в наборе решений | реестр организатора и версия набора решений инспектора |
| `model_version` | `pipeline-<версия>+<способ чтения>[/<модель>]` | версия конвейера, способ чтения объекта и модель, если она читала |

Способ чтения — `layer`, `tesseract` или `model` (#54): он выбирается при загрузке объекта
и попадает в протокол, потому что от него зависит, что вообще увидели правила. Обучаемой
модели у нас нет (Р-25); в `model_version` после косой черты стоит имя мультимодальной модели, которой читались сканы.

## Как добавить правило Матрицы

1. **Найти параметр в каталоге.** `docs/extracted/parameter_catalog_132.jsonl`: `source_pd`
   и `source_rd` говорят, в каком разделе искать значение, `criticality` — критичность.
2. **Описать правило в JSON** — `rules/matrix_queue<N>.json`, ключ — код параметра:

   ```json
   "SPZU-027": {
     "kind": "value", "labels": ["площадь озеленения"], "exclude": ["в том числе"],
     "rule": "last", "unit": "м2",
     "compare": {"type": "min_decrease", "result": "AREA_REDUCED"},
     "basis": "Уменьшение площади озеленения", "implemented": true
   }
   ```

   `kind` — как извлекать (`value`, `count`, `class`, `element_class`, ключевые разборы),
   `compare.type` — как сравнивать (`equal`, `min_decrease`, `min_absolute`,
   `class_downgrade`), `rule` — какую колонку брать, если шапка таблицы не распознана.
   Нереализованные параметры остаются с `"implemented": false` и полем `reason`.
3. **Модуль на Python нужен**, если значение не вытаскивается подписью и числом:
   когда нужно разобрать таблицу (`switchboards.py`), связать значение с элементом
   (`elements.py`) или сравнить множества (`smoke_fans.py`). Модуль отдаёт кандидатов
   `{value, raw, label, snippet}`, остальное делает `matrix_rules`.
4. **Проверки обязательны:** фрагменты настоящих страниц корпуса с указанием файла
   и страницы плюс не меньше пяти проверок на строках вне корпуса — с ожидаемым значением
   или с ожидаемым «не определено» (#41). Файл проверок — `tests/test_<тема>.py`,
   запускается как `python tests/test_<тема>.py`.
5. **Пересобрать находки шести объектов** и объяснить каждое изменение:
   `python -m pipeline.cli rules --object <объект>`. Изменения без объяснения — повод
   не принимать правило.

## Три стадии в записи правила

Кандидаты значений собираются по проектной, рабочей и исполнительной стадиям. Правило
сравнивает проект с рабочей стадией; построенное (`extraction.id`, `id_value`) сверяется
с рабочей стадией тем же правилом, при её отсутствии — с проектной (`matrix_rules.id_review`,
Д-53, #42). Итог сверки с ИД — в `extraction.id_check`, страницы ИД — в `evidence`.
Совпадение всех загруженных стадий — `comparison_result: EQUAL_ALL_AVAILABLE_STAGES`.
Значение только в ИД сравнивать не с чем — «сравнение невозможно» с пояснением. На корпусе
значение в ИД даёт один параметр, KR-055: в актах класс бетона берётся из марки смеси
«БСТ В25», элемент — из папки ограждения котлована, доказательство — первый акт серии (Д-52);
в протоколах испытаний бетона (`pipeline/test_protocols.py`, #62) — из строки таблицы:
конструкция, отметка со знаком и класс при прочности («Секция 2 на отм. -5.850 фундаментная
плита в/о Г- … 26,1 B30 | 87%»), у стороны ИД тогда есть `protocol_rows`, а в пояснении —
«значение исполнительной стадии — из протоколов испытаний бетона». Класс в такой строке —
проектный («Класс бетона по проекту»), фактический Вф стоит числом левее: сверка с рабочей
стадией отвечает «ту ли марку испытывали», а не «из чего построено» (Д-57).

Что читает машина, не решает молча (#41, Р-40). У стороны `extraction.pd/rd/id`:
`text_source: RECOGNIZED` — значение прочитано распознаванием; `doubtful` — распознанные
значения, отложенные как похожие на ошибку чтения (редкое рядом с частым, одна цифра
разницы, Д-51); `layer_conflict` — победило распознанное, а текстовый слой других страниц
даёт иное; `binding` у элементов — откуда взято значение (указания, страница, путь, лист).
`recognized_review` дописывает это в `extraction.detail` и ставит `needs_expert`, когда
нарушение опирается на распознанное значение, распознанное расходится со слоем или что-то
отложено; `extraction.recognized` — стадии с распознанным значением и нужно ли подтверждение.

## Чего здесь пока нет

## Стадия, марка и цепочки редакций

Задача #10. Сравнивать можно только сопоставимые документы: одна стадия, одна марка,
актуальная редакция.

```bash
python -m pipeline.cli revisions --object OBJ-RECHNIKOV-7-7 --workers 8
```

Команда дописывает поля в `documents.jsonl` и кладёт цепочки в `revisions.jsonl`, по одной
строке на цепочку. Связка листов `sheets.jsonl` не обязательна: без неё марка и шифр
берутся только из имён, а переиздания без общей марки в имени не связываются. Номер изменения
из штампа читается из текстового слоя PDF, распознавание и модель не нужны. Шесть объектов
считаются за минуту с небольшим на 8 процессах.

Идентификаторы, стадия и раздел из реестра не перезаписываются: стадию и раздел, которые
уже стоят (от реестра организатора, по пути или рукой инспектора, #39), команда не трогает
и заполняет только пробелы. Найденное своими правилами лежит рядом в `stage_detected`
и `section_detected`, прежнее значение раздела — в `section_registry`.

**Стадия и раздел** определяются одним правилом на весь конвейер — `registry.guess_stage`
и `registry.section_with_hint` (#39, #41): папка стадии сильнее имени файла, чужие названия
папок понимаются, «рд» внутри шифра «ЖС-РД-270121-П-ОПЗ» стадией не считается, сокращения
актов «АОСР» и «АООК» в имени файла означают исполнительную стадию. Если путь раздел
не называет, его даёт марка из шифра основной надписи (`section_source = MARK`
или `TITLEBLOCK_MARK` у актов, где штамп приложенной схемы называет комплект).

**Марка** — последний токен шифра до описания листа. Номер тома важнее короткой марки
после него, книга тома и корпус входят в ключ. Если есть связка листов, конкретная марка
из основной надписи заменяет номер тома из имени.

**Шифр документа** — самый конкретный из частых шифров основной надписи, если марка из имени
стоит в нём целиком, иначе шифр из имени. В набор шифров файла не попадают:
- шифры без марки: шифр комплекта «01-07/23-14-РД», штамп «СМК-ДК42-10», «ВН.ТЕР.Г» из адреса;
- шифры, частые в файлах с разными марками в имени: «245-0817-КМ-2/Н-3» на АР1 и РИО.

Латинские буквы-двойники в шифрах приводятся к кириллице. У исполнительной документации шифр
и марка со штампа не берутся: он копирует штамп листа РД, на который ссылается акт. Раздел
по нему определить можно, тогда `section_source` равен `TITLEBLOCK_MARK`.

**Редакция** собирается из трёх признаков: отметки в имени, таблица изменений над основной
надписью и близость по содержимому, то есть одинаковый набор шифров на страницах при почти
равном числе страниц. По содержимому сливаются только совместимые марки: номер тома с любой
маркой, «ПЗ» с «ПЗ1.2», но не «КЖ1» с «КЖ2.2» и не разные корпуса или книги. Порядок частичный:
- корректировки («кор», «корр.ГИП», переиздание по замечаниям) и изменения («изм»)
  между собой не сравниваются;
- версия («в1», «вер 2») сравнивается, только если корректировка и изменение равны;
- дата упорядочивает документы без отметок и проверяет порядок у документов с отметками;
- номер из штампа подставляется, только если в имени нет никаких отметок.

**Актуальная редакция** определена, если у цепочки ровно один последний документ и он
сравним со всеми остальными. Иначе цепочка получает `CLARIFICATION_REQUIRED` с причиной:
- «редакции не упорядочить», например «ОПЗ Изм 2» и «ОПЗ-кор3»;
- «одинаковая редакция у разных файлов», например два разных «ПОС-кор3»;
- «разные шифры проекта», например три поколения шифров Алтуфьевского;
- «переизданы отдельные листы»: слияние по листам делает #19.

Признак утверждения — ЭЦП, МГЭ или РнС в имени либо файл `.sig` рядом. Он не блокирует выбор
редакции: утверждения в файлах почти нет. Строгий вариант по ТЗ включается ключом
`--require-approval`: без признака утверждения актуальная редакция не определена.

У исполнительной документации цепочек нет: каждый акт отдельный документ. Файлы не в PDF,
например извещения об изменениях, редакциями комплекта не считаются.

**Актуальная редакция в правилах.** Правила Матрицы и сравнение по помещениям берут
значение из актуальной редакции цепочки (`matrix_rules.chain_index`, `revision_rank`):
устаревшая редакция видна инспектору в истории записи (`extraction.pd.revisions`), а если
актуальная значение не называет — берётся последняя из тех, где оно есть. Документ без цепочки
по-прежнему упорядочивается по имени файла (`revision_key`). Строка-копия реестра
(`duplicate_of`) места в цепочке не занимает: ранг и статус — у оригинала (Р-128). Цепочка,
порядок которой не определён, а редакции называют разные наборы значений, даёт записи «сравнение невозможно»
с `finding_status = CLARIFICATION_REQUIRED` и причиной — не нарушение и не «нарушения нет»
(ТЗ 9.1). В сервисе такая запись ждёт решения инспектора наравне с кандидатами; актуальную
редакцию он называет на экране файлов процесса (`POST …/files/{fileId}/revision`), выбор
идёт в журнал аудита (`FILE_REVISION_SET`) и вступает в силу при повторном разборе.

**Признак утверждения** — ЭЦП, МГЭ или РнС в имени либо файл `.sig` рядом. В корпусе
он редок, поэтому требуется не всегда: цепочка уходит на уточнение, только если утверждена
прежняя редакция, а последняя нет. Строгий режим ТЗ — ключ `--require-approval`.

Проверки — `python tests/test_revisions.py` и `python tests/test_revision_rules.py`.

## Помещения и марки систем с чертежей

```bash
python -m pipeline.cli plans --object OBJ-TYUMENSKAYA-5-GOLD-SEED
```

Задача #4. Экспликации дают не всё: из пяти помещений одной страницы-доказательства
в реестре экспликаций нашлось одно. Остальные подписаны прямо на плане, и достать
их можно только по координатам слов.

Вокруг номера помещения на листе обнаруживается устойчивая картина:

```
поз.169            маркировка позиции
140 Физического    номер и наименование
эксперимента       продолжение наименования
В2.9               марка вытяжной системы
```

Марка и есть предмет сравнения между стадиями: эталонное нарушение объекта
Тюменская-5 говорит, что в помещениях 140 и 142 отсутствует предусмотренная
проектом вытяжная вентиляция, а «В» — марка вытяжной системы.

**Марка достаётся ровно одному помещению — ближайшему.** Раздавать её всем номерам
в радиусе нельзя: на рабочем чертеже помещения перечислены таблицей, соседняя строка
отстоит на 0,029, и марка соседа попадает в радиус. Именно так помещению 142
доставалась чужая вытяжка из строки помещения 147.

**Радиус подобран замером.** На проектном листе марки стоят вертикальной стопкой над
номером, по три на помещение, на расстояниях 0,031, 0,039 и 0,049. Радиус 0,04 срезал
у каждого помещения третью марку, 0,05 забирает стопку целиком, дальнейшее расширение
к целевым помещениям ничего не добавляет.

**Листы отбираются по формату, а не по типу страницы.** Крупный чертёж
с экспликацией набирает больше четырёхсот слов и классифицируется как плотный
текст — так помечены три из шести эталонных страниц. Отбор идёт по длинной стороне
листа больше 1000 пунктов, то есть А3 и крупнее.

Проверка на шести страницах, которые организатор пометил как доказательства:
найдены все 19 целевых помещений из 19. По объекту целиком: 463 листа с помещениями,
6964 записи, 492 уникальных номера, 231 запись с маркой системы.

Прямоугольник выдаётся в двух системах координат: `bbox` от верхнего края листа,
как приходят слова, и `bbox_pdf` от нижнего, как публикует прямоугольники
организатор.

**Это генератор кандидатов, а не решение о нарушении.** Правило «вытяжка есть
в проектной и отсутствует в рабочей» по разделу ОВ даёт девятнадцать помещений,
среди которых обе нужные. Вытяжка помещения может быть показана на другом листе
того же комплекта, поэтому отсутствие марки на одном листе ничего не доказывает.
Сужает кандидатов сопоставление соответствующих листов, задача #19.

## Сравнение по помещениям: таблицы систем, пары листов, находки

```bash
python -m pipeline.cli systems --object OBJ-TYUMENSKAYA-5-GOLD-SEED      # таблицы и пары листов
python -m pipeline.cli rules   --object OBJ-TYUMENSKAYA-5-GOLD-SEED --queue 5   # находки
```

Задачи #21 и #37. Кандидаты по маркам на планах до находок не доводятся: на рабочем плане
марка стоит у воздуховода, номер помещения — в кружке посреди комнаты, а на Тюменской-5
подписи плана ещё и выведены кривыми. Сравнивается другое — таблица «Характеристика
отопительно-вентиляционных систем» формы ГОСТ 21.602: она есть в обеих стадиях и называет
обслуживаемое помещение словами.

| Модуль | Что делает |
|---|---|
| `vector_tables.py` | сетка таблицы из линий PDF в видимых координатах листа; текст ячейки — из слоя, а если слоя нет — распознаванием выреза ячейки без линий сетки, тремя прочтениями |
| `hvac_systems.py` | колонки по шапке, строки таблицы: обозначения систем, число систем, помещения, позиции оборудования, расход; номер помещения принимается двумя прочтениями из трёх |
| `stroke_glyphs.py` | #48: обозначения и номера на листах без слоя по форме глифов-штрихов; образцы знаков — из ячеек того же листа, которые Tesseract прочёл уверенно; цифры не правятся, ячейка читается только целиком |
| `sheet_pairs.py` | #21: для листа ПД — листы РД по доле общих помещений, дисциплине и близости наименования листа из основной надписи (дословно совпавшее наименование идёт первым); для помещения — лист, где оно есть |
| `vent_units.py` | установки с расходом и давлением из перечня оборудования; помещение установки — ближайший номер на проектной схеме, расстояние в миллиметрах листа |
| `room_compare.py` | #37: поиск таблиц по объекту, решение по помещению, находки с рамками на листах обеих стадий |

Команда `systems` пишет `build/<объект>/hvac_systems.jsonl` (строки таблиц обеих стадий)
и `build/<объект>/sheet_pairs.jsonl` (пары листов). Находки строит обычная команда `rules`:
IOS4-078 и IOS4-079 — правила пятой очереди видов `room_systems` и `vent_units`, поэтому
в сервис, протокол и сдачу они попадают тем же путём, что и остальные правила Матрицы.

Таблицы ищутся только в томах отопления и вентиляции (раздел реестра или путь файла):
копия таблицы в томе охраны окружающей среды источником не считается. Сначала проверяются
страницы, где текст похож на таблицу систем, затем листы с крупной сеткой без текстового
слоя, затем листы продолжения в обе стороны. Сбор идёт по стадиям и обрывается, как только
у одной из стадий таблицы нет: на объекте без рабочих томов ОВ проверка занимает меньше секунды
и отвечает причиной — «в рабочей стадии нет документов отопления и вентиляции».

Распознавание ячеек двух томов Тюменской-5 (≈1 570 ячеек, три прочтения) занимает 3–4 минуты
и кешируется дважды: прочтения ячеек (`*.hvacocr.json`) и разобранные строки (`*.hvac.json`).
Правка правил разбора меняет `CACHE_VERSION`, и строки собираются заново из сохранённых
прочтений, без Tesseract. `PIPELINE_TABLE_OCR=0` отключает распознавание: таблицы с текстовым
слоем читаются по-прежнему, таблицы без слоя пропускаются.

На Тюменской-5 так найдены 6 эталонных точек из 10 (все шесть по вентиляции), прежде было 0.

Задача #8. На входе находки по `contracts/finding.schema.json`, на выходе
`submission.json` по схеме организатора, проверка по этой схеме и отчёт о потерях

в своём эталоне, а не на то, что написано в ТЗ.

### Что показывает проекция на настоящей находке

Сравнение марок вытяжных систем на паре листов ИОС4, страницы 88 проектной
и 18 рабочей, даёт шесть помещений. Проекция превращает находку в шесть записей
сдачи и проходит схему организатора. Балл зависит от того, сопоставлена ли находка
с Матрицей:

| Код параметра находки | Совпало | Точность | Полнота | Локализация | Балл |
|---|---|---|---|---|---|
| `FREE-VENT-001`, вне Матрицы | 0 из 10 | 0,000 | 0,000 | — | 10,00 |
| `IOS4-078`, из Матрицы | 4 из 10 | 0,667 | 0,400 | 8 из 8 | 59,00 |

Локализация в обоих случаях безупречна: все воспроизведённые доказательства попали
в точный файл и страницу. Разница целиком в коде параметра. Пока находка не
сопоставлена с Матрицей, правило отождествления заводит её в свободный поиск,
где она сравнивается с чужими помещениями и не совпадает ни с чем.

Вывод для плана: проекция и локализация готовы, узкое место — сопоставление находки
с параметром Матрицы. Балл 59 это потолок гейта, он держится пропуском критических
точек на других листах, а не качеством проекции.
